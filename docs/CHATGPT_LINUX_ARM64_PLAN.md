# Siguiente incremento: ChatGPT Linux ARM64 con Codex

**Estado posterior EXP05:** el diagnóstico del helper que este plan dejaba pendiente fue autorizado y ejecutado. El comando protegido no arranca; kernel sin USER_NS/PID_NS/Landlock. **La ruta app oficial/PRoot queda bloqueada en la configuración actual**, sin instalación o login. Se recomienda investigar app-server/UI móvil/ejecutor controlado, sin ejecutar esa nueva fase. [Resultado del sandbox y evidencia](CODEX_SANDBOX_REPORT.md). Los pasos siguientes se conservan como plan anterior, no como instrucción para seguir instalando.

**Actualización EXP04, 2026-10-20: auditoría ejecutada; instalación bloqueada antes de aplicar cambios.** El usuario autorizó descargar/auditar y, si no había bloqueos importantes, instalar y abrir la app sin credenciales. Se verificó el paquete oficial **26.1013.40934 ARM64**, sus firmas y su resolución APT. La configuración real del kernel deshabilita user/PID namespaces; se activó la parada de seguridad solicitada. **No se instaló ni lanzó ChatGPT.** [Informe y siguiente diagnóstico mínimo pendiente de autorización](CHATGPT_LINUX_ARM64_REPORT.md).

La documentación oficial actual publica una **preview para Debian 13 y ARM64**, con paquete `.deb`, instalación por APT y acceso a Codex dentro de ChatGPT. Su soporte declarado corresponde a distribuciones desktop; **no acredita esta configuración Android/PRoot**. [OpenAI Docs: aplicación Linux](https://learn.chatgpt.com/docs/linux/linux-app). Fuentes consultadas y hashes: [registro](validation/mestry-x11-20261020T052004Z/next_phase_official_sources.json).

1. **Fijar el artefacto para revisión — completado en EXP04.** `.deb` ARM64 obtenido del enlace oficial; SHA-256 `9ab2cbbaf33cebeaa1e06eb5cab78128936f927a0d97bf00e40694e5f31c629b`, firmas del paquete y del índice verificadas con la clave incluida, cuyo anclaje inicial es HTTPS oficial. Conservar la versión descargada y no sustituir `latest` silenciosamente.
2. **Inspeccionar sin ejecutar instaladores.** Leer control, dependencias y scripts de mantenimiento con `dpkg-deb`. Extraer para revisar binarios ELF/AArch64, requisitos de glibc, launcher, helpers y permisos. Identificar cualquier repositorio que pretenda añadir. No usar instaladores por tubería ni instalar otra arquitectura por emulación.
3. **Simular dependencias y preparar reversión.** Guardar inventario y estado privado de la instancia; simular la transacción APT, detallar cambios/espacio y resolver solo dependencias necesarias. Evaluar D-Bus de sesión y almacén de credenciales soportado a partir del paquete real. No añadir XFCE o actualizar todo Debian por defecto. La instalación, si se autoriza, usaría el root aparente de PRoot exclusivamente para paquetes; la app se ejecutaría como `mestry`.
4. **Primera apertura sin credenciales.** Usar el display Unix autenticado existente y un home/proyecto de prueba. Revisar ventana, foco, teclado, fuentes, archivos sintéticos, procesos, memoria y logs; separar fallos de dibujo de fallos de seguridad. Medir estabilidad durante la ventana acordada, incluyendo el tramo de 30 minutos de V01.3 si se pretende aceptarlo completo.
5. **Dos puertas de seguridad distintas.** Conservar la protección del renderer y comprobar por separado el control de comandos del harness que realmente incorpora esa app. Probar operaciones deterministas permitidas y denegadas con archivos sintéticos, verificando el efecto real. La documentación Linux de Codex utiliza `bubblewrap` o un helper con namespaces no privilegiados; su funcionamiento bajo el kernel Android sigue por comprobar. [OpenAI Docs: sandbox](https://learn.chatgpt.com/docs/sandboxing). Una CLI externa funcionando no certifica el helper de la app.
6. **Revisar resultados antes del login.** Informar versión, compatibilidad, dependencias, recursos, errores y fronteras demostradas. Si requiere root real, `--no-sandbox`, acceso completo sin límites o desactivar protecciones, detener la rama conservando el fallo. Si el harness solo permite su prueba tras autenticar, registrar la dependencia y solicitar aparte una cuenta/entorno de prueba y límites de datos/gasto. No copiar credenciales del PC.

Las etapas 2–3 se ejecutaron como inspección y simulación; **119 paquetes nuevos y una actualización fueron propuestos, ninguno aplicado**. Las etapas 4–6 permanecen sin ejecutar. La continuación queda sujeta a la revisión del bloqueo y del diagnóstico mínimo descrito en el informe; no se propone omitir sandboxes.

El alcance no incluye reinicio, prueba de Boot, VNC/red pública, inferencia, sincronización Drive ni Device Agent. El funcionamiento de `xterm` no certifica la app o sus controles, y el éxito aparente de `unshare` dentro de PRoot tampoco demuestra un namespace real.
