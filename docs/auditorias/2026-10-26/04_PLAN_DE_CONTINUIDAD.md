# MESTRY — Plan de continuidad propuesto

Fecha: **2026-10-26**. **Todo este plan es PROPUESTO salvo las decisiones ya identificadas como APROBADO / CONGELADO en [03](03_TRAZABILIDAD_ARQUITECTONICA.md).** No se ejecutó implementación, sincronización o reconfiguración para cumplirlo. La autorización vigente termina en la auditoría/documentación.

## 1. Objetivo inmediato y restricciones

El incremento recomendado es **leer desde el S25 un documento explícitamente autorizado, usando el broker ya existente en el S23, y mostrar contenido, ID/origen y versión observada**. Primero deben aclararse autoridades y sincronizadores para que ese incremento no publique ni sobrescriba documentos por accidente.

No se reinstala Codex ni se repite su validación básica: el usuario ya la aceptó y hay evidencia histórica. No se introduce servidor, NAS, base vectorial, webhook, nueva cuenta, nuevo cliente OAuth ni más scopes para lograr la primera lectura. El objetivo del piloto de desarrollo/documentos **no reemplaza el MVP de voz de la Etapa 1**; la continuidad del asistente requiere recuperar sus originales y confirmar su secuencia de producto.

Complejidad relativa: **baja** = lectura/registro y cambio acotado; **media** = coordinación entre componentes o pruebas con estado; **alta** = múltiples subsistemas/formatos o recuperación/concurrencia. No son horas comprometidas ni estimaciones de rendimiento. El riesgo se refiere a la tarea futura, no a una autorización para ejecutarla.

## 3. Orden recomendado de las próximas tres acciones

1. **Completar C01–C04 como una intervención de diagnóstico/documentación:** recuperar visibilidad, conocer el par S23 y conciliar autoridades. Windows tiene fallos registrados y WSL tiene resync bidireccional; corregirlos a ciegas aumenta el riesgo. La salida inicial debe ser un mapa y un cambio propuesto revisable, no otra sincronización.
2. **Preservar código y fuentes normativas, C05–C06:** convertir el código reproducido en una línea base duradera bajo alcance aprobado, conservar evidencias originales y recuperar los cinco documentos. Mantener el piloto funcionando sin tocar su instalación.
3. **Aceptar la lectura mínima C07 y luego la independencia operativa C09:** un archivo existente autorizado, trazado por ID y versión, desde el cliente instalado. Es el menor incremento útil sin publicación ni RAG prematuros. Si aparecen límites del broker, preparar un cambio acotado con pruebas antes de pedir aprobación para desplegarlo.

La continuidad del producto se decide con los originales recuperados: no se cambia la prioridad de voz por el hecho de que haya más código de desarrollo remoto que código del asistente.

## 4. Decisiones y acciones que requieren aprobación posterior

| Decisión / acción | Material concreto que debe revisarse antes de solicitar aprobación | Límite que debe conservarse |
|---|---|---|
| Cambiar direcciones, filtros, borrados, scopes o frecuencia de FolderSync/rclone | Pares/IDs exactos, diff de filtros/configuración, comparación de archivos y recuperación | No ejecutar `init`, `resync`, borrado o restauración por la sola existencia de un fallo |
| Crear Git, consolidar fuentes fuera de caché o mover carpetas | Lista de archivos, ubicación, exclusiones, hashes y efecto sobre sincronización | Sin credenciales/datos privados en commit; sin push autorizado implícitamente |
| Activar/redirigir/ampliar publicador o editar originales | Archivo y destino vigentes por ID, preview/diff, riesgo, idempotencia y readback | No restaurar Review/Horus ni ampliar allowlist o OAuth por defecto |
| Escribir archivos de prueba en carpeta sincronizada | Carpeta temporal exacta, contenido sintético, autores, hash, límite y limpieza | No originales importantes; prueba de borrado/conflicto solo aprobada expresamente |
| Reiniciar, detener procesos, provocar fallo de bridge/UID o probar recuperación | Protocolo, fixture/tarea, backup, rollback e intervención humana prevista | No usar un ensayo de estabilidad como permiso general de configuración |
| Extender `never/dangerFullAccess` a proyectos/documentos reales | Alcance de datos y amenazas, fronteras efectivas, minimización y permisos | La aceptación histórica en Horus/piloto no es aprobación del Action Controller general |
| Adoptar cambios de arquitectura de producto | Texto de decisión concreto contrastado con los seis originales y brecha observada | Solo el usuario puede modificar decisiones congeladas; no editar originales para resolver contradicciones |
| Introducir nuevas dependencias, modelos o infraestructura | Fallo/necesidad medidos y alternativa mínima | No servidor/vector DB/Note20 nuevo para resolver una lectura directa |

No se necesita aprobar ninguna reconfiguración para cerrar **esta** auditoría: los hallazgos y limitaciones ya quedan documentados. Las aprobaciones anteriores se solicitan cuando exista una propuesta específica y revisable de la fase siguiente; no se interpreta silencio como autorización.
